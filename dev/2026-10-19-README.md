# From Data to Digital-Opportunity Intelligence

A hands-on learning repository for building fluency across relational query languages, logic programming, semantic knowledge graphs, property graphs, graph traversal, path querying, and network science.

This repository accompanies my learning roadmap for **SQL, first-order logic, Prolog, Datalog, RDF, SPARQL, Cypher, GQL, Gremlin, graph path querying, and network science**. Rather than treating each language as an isolated technology, the project uses one continuing domain model: a small **Michigan Digital Opportunity Knowledge Graph**.

The objective is not simply to learn syntax. It is to understand how the same real-world system looks when represented as tables, logical statements, semantic triples, property graphs, traversals, paths, and networks, and to recognize which representation fits the question being asked.

## Why This Repository Exists

My work with **MiGreatDataLake**, the **Digital Opportunities Intelligence Network (DOIN)**, knowledge graphs, community data, and research increasingly sits at the intersection of data engineering, semantics, network science, and causal inquiry. That makes understanding query languages more than a database skill. It is part of understanding how information becomes knowledge and how relationships become analyzable structures.

The long-term progression behind this repository is:

```text
Data
  ↓
Relationships
  ↓
Semantics
  ↓
Knowledge
  ↓
Graph Structure
  ↓
Research Questions
  ↓
Statistical Models
  ↓
Causal Inquiry
```

A knowledge graph is therefore not the endpoint. It is a connective analytical layer between data and increasingly sophisticated forms of inquiry.

## One Domain, Many Representations

The central learning strategy is simple: **keep the domain relatively stable while changing the information model and query paradigm**.

The working domain may include:

- Communities and counties
- Schools and intermediate school districts
- Libraries
- Nonprofits
- Tribal Nations
- Broadband providers
- Workforce organizations
- State agencies
- Universities and research organizations
- Programs and initiatives
- Funding sources
- Infrastructure projects

Representative relationships include:

```text
Community → LOCATED_IN → County
Organization → SERVES → Community
Organization → PARTNERS_WITH → Organization
Organization → PARTICIPATES_IN → Program
ISP → PROVIDES_SERVICE_TO → Community
Agency → FUNDS → Program
Program → SUPPORTS → Community
```

The exact model will evolve as the project develops. Changes to the model should be intentional and documented so that differences among representations remain part of the learning record.

## What Each Stage Should Produce

Each stage should preserve four core learning artifacts.

### 1. Data Model

Document how the digital-opportunity ecosystem is represented at that stage. A relational schema, RDF vocabulary, property-graph model, or rule set is itself part of the research record.

### 2. Working Queries or Rules

Maintain at least a small progression from simple retrieval to multi-hop or recursive questions. The emphasis should be on understanding what each expression means, not accumulating query files.

### 3. Query Journal

For important queries, explain in plain English:

- What question am I asking?
- What information does the query rely on?
- What assumptions are embedded in it?
- What does the result establish?
- What does the result **not** establish?

This is especially important as the project moves from retrieval into inferred relationships and network analysis.

### 4. Comparison Note

At the end of each stage, document what became easier, harder, or conceptually different compared with the previous representation.

For example, the valuable lesson in rewriting an SQL query in SPARQL or Cypher is not merely learning different punctuation. The comparison should reveal how relational joins, RDF graph patterns, property-graph patterns, and traversals express relationships differently.

## Core Query Ladder

The repository should move through increasingly sophisticated classes of questions.

### Descriptive

> What organizations operate in this county?

### Relational

> Which organizations serve the same communities?

### Semantic

> Which entities are connected through explicitly defined types of relationships?

### Path

> How is a community connected to a state program in the modeled data?

### Deductive

> Under explicitly defined rules, which communities could be connected to workforce resources through partner organizations?

### Structural

> Where does the represented network contain clusters, bridges, or disconnected components?

### Comparative

> How does the observed institutional network surrounding rural communities differ structurally from the network represented around urban communities?

### Statistical

> Is observed institutional network connectivity associated with measured digital-opportunity outcomes?

### Causal

> Under an appropriate research design, is there evidence that a particular intervention or network condition causes a change in an outcome?

The last two questions require methods beyond graph querying alone. Network structure can generate hypotheses and explanatory variables, but association and graph position should not be treated automatically as causal evidence.

## Provenance and Research Discipline

A major principle of this repository is maintaining clear provenance as the work becomes more analytical. Every result should be distinguishable as one of the following:

- **Source data:** an observation or value obtained from an identified source.
- **Modeled relationship:** a relationship explicitly represented from source evidence.
- **Derived result:** something produced through a documented query or rule.
- **Network measure:** a computed property of the modeled graph.
- **Interpretation:** a reasoned explanation of what a result may mean.
- **Hypothesis:** an empirical proposition requiring testing.
- **Causal claim:** a claim requiring an appropriate identification strategy and supporting evidence.

This distinction matters because a knowledge graph can make relationships visible without proving why those relationships exist, whether they are complete, or whether they cause observed outcomes.

## Guiding Principle

The measure of progress is not how many languages I can list. It is whether I can recognize the nature of the question in front of me.

Is it relational? Semantic? Deductive? Structural? Navigational? Statistical? Causal?

That distinction determines what data model, query language, analytical method, and evidence are appropriate. The repository is intended to make that progression visible through working examples rather than leave it as an abstract framework.
